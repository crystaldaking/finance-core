# Upgrading to v1.2

## Validation and stored data

- Identifiers and decimal inputs must match the entire format. Before upgrading, check historical identifier columns for a trailing LF and plan a data repair for any matches. Check for collisions with existing accounts, assets, references, and idempotency identities before making corrections.
- Ordinary ledger append accepts new transactions without reversal state. Reversal repositories must compare against the stored original, preserve its postings, and reject duplicate ids and references. Review existing adapters against the [adapter guide](../adapters.md).
- Rules now accept at most one minimum and one maximum at calculation time. Give fee operations and labels nonblank names. Explicit fee results require nonnegative gross and total fee amounts. Maximum adjustments can still appear as negative breakdown lines.

## Fingerprints

The persisted SHA-256 string format is unchanged. New fingerprints sort map keys by bytes, including numeric-looking string keys. For records written by v1.1, the runner also compares the legacy digest for the incoming field order. If an older record used a different order that changes its legacy digest, replay can return a fingerprint conflict. Complete or drain affected in-flight requests before a mixed-version rollout, or retry them in the original field order during their retention window. Upgrade shared-store adapters to compare with `matchesStored()`.

If an adapter joined scope and key with a literal colon, review the original pair values and migrate the store to a composite key. Resolve ambiguous historical rows before reusing them.

## Optional fields

Use `occurredAt` for ledger business time, and `asOf` for derived balances and exchange rates. Adapters can use `null` for records created before these fields existed. Exchange rates can also carry an optional source.
